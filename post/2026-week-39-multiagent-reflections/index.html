2026년 38~39주차 | 모델이 막혔을 때, 다른 모델이 도와줄 수 있을까

MCP 도구를 추가하다가 /reload 이후에도 목록이 갱신되지 않는 문제를 만났다. 모델마다 달랐던 디버깅 결과를 보며, 사람이 매번 개입하지 않아도 에이전트끼리 협력해 문제를 해결할 방법을 고민했다.

2026-09-27

38주차부터 39주차까지 약 2주 동안 한 가지 질문을 붙잡고 실험했다. 모델이 문제를 해결하지 못할 때, 사람이 개입하는 대신 다른 모델이 도와 끝까지 마무리할 수 있을까? 처음에는 역할을 나누면 될 줄 알았지만, 직접 해보니 작업 맥락을 공유하고 실제 완료 여부를 검증하는 일이 더 중요했다.

오픈코드를 커스터마이즈하면서 MCP 도구를 추가하던 중 이상한 문제를 만났다. 새 도구를 추가하고 /reload를 실행해도 도구 목록이 제대로 갱신되지 않았다. 캐시 때문에 변경 내역이 반영되지 않는 상황이었는데, 내부적으로는 200 OK 응답이 돌아왔다.

요청은 성공했다고 나오는데 정작 도구는 추가되지 않았다. 실패 응답이라도 보였다면 원인을 좁히기 쉬웠을 텐데, 겉으로는 정상인 것처럼 보이니 더 답답했다.

같은 문제를 맡겼는데 모델마다 결과가 달랐다

이 문제를 여러 모델에 맡겨 봤다.

모델 디버깅 결과
gemini-flash 정상적으로 동작한다고 판단했지만, 실제로는 도구가 추가되지 않은 상태였다.
gpt-terra 문제를 인식했지만 스스로 해결하겠다며 할당량을 다 쓸 때까지 시도했다. 정작 원인과 다른 부분을 건드렸고, 결국 해결하지 못했다.
gpt-astra 문제를 찾아내고 디버깅을 완료했다.

같은 문제를 두고도 모델마다 결과가 달랐다. 특히 gpt-terra의 모습이 기억에 남았다. 문제가 있다는 사실은 알았지만, 잘못된 방향으로 가고 있다는 점은 알아차리지 못한 채 시도를 계속했다.

처음에는 단순히 모델마다 디버깅 능력이 다르다고 생각했다. 그런데 다시 돌아보니 더 중요한 문제가 있었다. 모델은 자신이 잘못된 방향으로 가고 있다는 사실조차 인지하지 못할 때가 있다.

실제로는 중간중간 내가 개입해야 했다. 결과가 맞는지 확인하고, 엉뚱한 부분을 수정하고 있으면 지적하고, 필요하면 다른 모델에 맡겼다. 모델을 바꿀 때마다 상황을 다시 전달하는 것도 내 몫이었다.

이런 개입을 에이전트들끼리 대신할 수는 없을까? 처음 떠올린 것은 가벼운 모델이 작업을 진행하다 막히면 강한 모델에게 도움을 요청하고, 해결한 뒤에는 다시 작업을 이어가는 방식이었다.

여기에는 비용에 대한 고민도 함께 있었다. 그렇다고 처음부터 토큰 비용을 줄이는 것 자체가 목적이었던 건 아니다. 내가 매번 끼어들지 않아도 문제를 끝까지 해결하면서, 가능하면 불필요한 토큰 소비도 줄이는 구조를 생각하게 된 것이다.

Gemini Robotics 2에서 발견한 힌트

이런 역할 분담을 생각할 때 떠오르는 사례가 있었다. 유튜브 영상을 통해 알게 된 Google DeepMind의 Gemini Robotics 2였다.

Gemini Robotics 2를 처음 접한 유튜브 영상 원본.

인상적이었던 부분은 주변 상황을 이해하고 깊이 추론하며 계획하는 모델과, 실제 행동을 수행하는 VLA(Vision-Language-Action) 모델이 협력하는 구조였다. 판단과 실행을 서로 다른 역할로 나눈다는 점이 흥미로웠다.

그 구조를 보면서 이런 생각이 들었다. 굳이 모든 행동을 깊이 생각하는 모델이 직접 수행할 필요가 있을까?

물론 로봇의 행동 제어와 소프트웨어 에이전트의 디버깅은 다른 문제다. 하지만 서로 다른 역할을 가진 모델이 협력한다는 발상은, 내가 겪은 문제를 다른 방식으로 바라보게 해줬다.

System 1과 System 2를 떠올리다

Gemini Robotics 2의 구조를 보면서 대니얼 카너먼의 『생각에 관한 생각』에서 접했던 System 1과 System 2의 구분이 떠올랐다.

System 1은 빠르고 직관적으로 반응하는 사고 방식이고, System 2는 느리지만 의식적인 집중과 숙고가 필요한 사고 방식이다. 실제로 뇌 안에 두 기관이 따로 있다는 의미가 아니라, 인간의 사고를 설명하기 위한 개념적인 구분이다.

물론 Google DeepMind가 Gemini Robotics 2에 이 이론을 직접 적용했다고 말하는 것은 아니다. 내 눈에는 깊이 생각하는 모델과 빠르게 행동하는 모델이 협력하는 모습이 이 두 사고 체계와 닮아 보였다.

이 발상을 소프트웨어 에이전트에도 적용한다면, 모델이 어려운 문제를 만날 때마다 내가 직접 개입할 필요가 줄어들지 않을까?

무거운 모델은 판단하고, 가벼운 모델은 실행한다

내가 생각한 구조는 비교적 단순했다.

가벼운 모델이 먼저 실행 가능한 작업을 수행한다. 문제가 해결되었는지 실제 결과로 확인하고, 예상과 다른 결과가 나오거나 스스로 판단하기 어려워지면 무거운 모델의 도움을 요청한다. 무거운 모델은 그때까지의 실행 결과와 오류를 바탕으로 원인을 분석하고 다음 방향을 잡아준다.

중요한 것은 단순히 모델을 바꾸는 것이 아니라, 언제 도움을 요청해야 하는지 에이전트가 판단하고, 앞선 작업의 맥락을 이어서 협업하는 것이다.

모든 단계에 무거운 모델을 쓰지 않더라도 어려운 순간에는 그 능력을 활용할 수 있다면, 사용자 개입과 토큰 비용을 함께 줄일 가능성이 있다. 물론 실제로 비용이 줄어드는지는 검증해야 할 문제다.

막혔다는 사실조차 모른다면

처음에는 가벼운 모델이 작업을 진행하다 어려운 문제를 만나면, 더 강한 모델에게 도움을 요청하는 구조를 떠올렸다. 하지만 MCP 디버깅 경험을 돌아보니 한 가지 의문이 남았다.

모델이 자신이 잘못된 방향으로 가고 있다는 사실을 모른다면, 언제 도움을 요청할 수 있을까?

이후 접한 Claude의 사이버 보안 평가 사례를 다룬 영상에서도 비슷한 문제를 발견했다. 영상에 따르면 Claude는 자신이 실제 인터넷에 연결되어 있을 가능성을 의심하고 확인까지 시도했지만, 결국 시뮬레이션 환경이라는 잘못된 판단을 내렸다. 이후 이메일 인증과 결제 같은 예상 밖의 장애물을 만나면서도 그 전제를 다시 검토하기보다는 해결해야 할 과제로 받아들이며 작업을 계속했다.

Claude의 사이버 보안 평가 사례를 다룬 유튜브 영상 원본.

물론 이 사례에는 평가 환경이 실제 인터넷에 연결된 설정 오류도 있었다. 그래서 사건 전체를 모델의 판단 문제만으로 설명할 수는 없다. 다만 내가 주목한 것은 강력한 모델조차 한번 잘못된 전제를 확신하면, 이후 나타나는 신호들을 그 전제에 맞춰 해석하며 계속 진행할 수 있다는 점이었다.

그렇다면 멀티에이전트 구조에서 중요한 것은 단순히 어려운 작업을 다른 모델에게 넘기는 기능만이 아닐지도 모른다. 작업을 수행하는 에이전트와 별개로, 진행 상황과 판단의 근거를 독립적으로 검토하는 역할도 필요할 수 있다. 실행 중인 모델이 스스로 도움을 요청하지 않더라도 다른 관점에서 잘못된 방향을 발견하고 바로잡을 수 있어야 한다.

다만 검토하는 모델도 틀릴 수 있다. MCP 도구가 200 OK를 반환했다고 끝난 것이 아니었던 것처럼, 다른 모델의 의견만 듣는 데서 멈추지 않고 실제 도구 목록이 갱신되었는지 같은 완료 조건을 확인하는 과정이 중요하다.

처음에는 모델 사이의 역할 분담을 고민했지만, 점점 에이전트가 서로의 판단을 검증하고 방향을 바로잡는 협업 구조에 관심이 옮겨가고 있었다.

단순히 모델 두 개를 붙인다고 해결되지는 않았다

처음에는 역할만 나누면 될 것 같았다. 한쪽이 판단하고 다른 쪽이 실행하면 내가 직접 모델을 전환하지 않아도 되지 않을까 싶었다.

하지만 실제로 여러 에이전트의 사용 방식과 협업 구조를 살펴보니 문제가 조금 더 복잡했다. 실행하는 에이전트가 지금 무엇을 하고 있는지, 어떤 오류를 만났는지, 왜 계획을 바꿔야 하는지를 판단하는 에이전트가 알아야 했다. 반대로 판단하는 에이전트가 매번 모든 실행 기록을 읽어야 한다면, 절약하려던 토큰 비용이 다시 늘어날 수 있었다.

결국 모델의 역할을 나누는 것만큼 언제 도움을 요청할지, 그때 어떤 맥락을 전달할지가 중요했다.

Orca와 Hermes를 써보며 느낀 한계

9월 초부터 Orca와 Hermes를 사용하고, 특히 9월 중순에는 작업을 위임하고 결과를 검토하는 방식을 비교해 봤다.

Orca는 잘 만들어진 ADE(Agent Development Environment)라는 인상을 받았다. 여러 작업과 에이전트의 진행 상태를 관리하는 데 장점이 있었다. 다만 내가 경험한 멀티에이전트 방식은 메인 에이전트가 목표와 작업을 서브에이전트에 위임하고, 서브에이전트가 결과를 정리해 보고하는 구조에 가까웠다.

이 방식이 쓸모없다는 뜻은 아니다. 해야 할 일이 양적으로 많고 영역별로 나눌 수 있다면 여러 서브에이전트에 작업을 맡기는 것이 효과적이다. 하지만 하나의 어려운 문제를 풀다가 잘못된 방향으로 빠지는 상황에서는 이야기가 달랐다.

서브에이전트가 자신의 접근이 맞다고 판단한 채 계속 작업하면, 스스로 도움을 요청하지 않을 수 있다. 메인 에이전트도 서브에이전트가 정리해 보낸 보고만 받는다면 그 판단이 어디서 어긋났는지 알아차리기 어렵다. 결국 메인이 직접 문제를 확인해야 하는 순간에는 서브에이전트가 열어봤던 파일과 실행 내역을 다시 찾아 읽어야 한다. 일은 위임했지만, 문제를 파악하는 비용은 다시 발생하는 셈이다.

Hermes도 사용해 보니 구현 방식과 기능의 세부 사항은 달랐지만, 내가 경험한 서브에이전트 협업은 비슷한 한계를 갖고 있었다. 트리 형태로 작업을 위임하고 하위 에이전트가 요약한 결과를 상위 에이전트에 전달하는 구조에서는, 상위 에이전트가 하위 에이전트의 작업 과정을 그대로 공유받는 것은 아니었다.

생각해 보면 회사의 보고 체계와도 닮았다. 상급자가 하급자에게 일을 맡기고, 하급자는 끝낸 일을 요약해서 보고한다. 여러 업무를 분담하고 관리하기에는 자연스러운 방식이다. 하지만 지금 내가 원하는 것은 단순한 업무 분담이 아니라, 한 에이전트가 잘못된 방향으로 가고 있을 때 다른 에이전트가 그 과정을 보고 함께 문제를 해결하는 것이었다.

그래서 필요한 것은 에이전트별 작업 맥락이 분리되어 결과만 전달되는 구조가 아니라, 작업 중 확인한 정보와 판단 근거를 서로 공유할 수 있는 환경이라고 생각했다. 서브에이전트가 어떤 파일을 열어봤다면 메인 에이전트도 그 내용을 필요할 때 바로 확인할 수 있어야 한다. 어떤 도구를 실행했고 무슨 오류가 났는지, 왜 그 방향으로 판단했는지도 공유되어야 한다. 그래야 메인이 처음부터 다시 조사하지 않고 진행 중인 작업을 검토해 방향을 바로잡을 수 있다.

물론 모든 파일 내용과 실행 기록을 모든 모델의 문맥에 매번 통째로 넣으면 비용이 커질 것이다. 내가 원하는 것은 무조건 같은 대화 기록을 복제하는 것이 아니라, 같은 작업 공간의 근거와 진행 상황을 공유하고 필요한 순간에 함께 들여다볼 수 있는 협업 환경에 가깝다.

그렇게 생각하고 나니 결론도 달라졌다. Orca나 Hermes의 기본 위임 구조를 그대로 사용하는 것만으로는 내가 원하는 협업을 구현하기 어려웠다. 그래서 작업 맥락을 공유하고 서로 검토할 수 있도록 직접 커스터마이즈해서 사용해 봤다.

커스터마이즈해서 직접 실험해 보니

구성하는 과정부터 쉽지는 않았다. 에이전트들이 작업 과정과 실행 결과를 어떻게 공유할지, 어느 모델이 어떤 시점에 개입해야 할지 고민해야 했다.

처음부터 에이전트들이 자동으로 협력하는 구조를 완성한 것은 아니었다. 우선 내가 다음 턴에 동작할 모델을 직접 지정하면서, 서로 다른 모델이 하나의 작업을 이어서 수행할 수 있는지 테스트했다.

그런데 실제로 사용해 보니 또 다른 문제가 드러났다.

예를 들어 아스트라가 전체적인 계획과 작업 방향을 잡고 루나 같은 가벼운 모델과 함께 작업을 진행할 때, 계획에 포함된 열 가지 작업이 모두 완료되는 경우는 없었다. 루나는 간단한 작업은 비교적 잘 처리했지만, 복잡한 작업이나 검증 단계에서는 함께 정한 계획의 일부가 누락되곤 했다.

특히 정형화된 테스트를 실행하는 것과 실제 사용 흐름을 확인하는 E2E 검증 사이에 차이가 있었다. 이미 만들어진 테스트를 실행하는 일은 비교적 잘 수행했지만, 아스트라가 지시한 E2E 테스트와 검증은 충분히 수행하지 않는 경향이 있었다.

그렇다고 상위 모델이 이 문제를 발견하지 못한 것도 아니었다. 아스트라는 해당 작업이 아직 완료되지 않았다고 지적했다. 나 역시 루나에게 간단히 “아스트라의 지시대로 수행해” 라고 다시 지시했다.

루나가 아무것도 하지 않은 것은 아니었다. 추가 작업을 수행하기는 했다. 하지만 다시 확인해 보면 여전히 요구한 수준까지 완료하지 못한 부분이 남아 있었다.

반면 같은 작업을 아스트라에게 직접 맡겼을 때는 제대로 완료했다. 적어도 내가 실험한 상황에서는 지시가 모호해서 생긴 문제만은 아니었다. 미완료를 알아차리는 능력과 지시받은 작업을 끝까지 수행하는 능력은 별개였고, 모델에 따라 그 차이가 드러났다.

결국 모델 사이에 작업 맥락을 공유하고 검토하는 구조를 만든다고 해서 협업이 완성되는 것은 아니었다. 검토 결과를 실행에 반영하고, 요구한 작업이 실제로 완료될 때까지 확인하는 과정까지 필요했다.

그리고 한 가지 의문이 더 생겼다. 상위 모델이 정확하게 지시하고 미완료 항목까지 지적했는데도 하위 모델이 끝내 수행하지 못한다면, 같은 모델에 계속 재시도하게 하는 것이 과연 효율적일까?

난이도에 따라 협업 구조를 선택해 보니

그렇다고 멀티에이전트가 비효율적이기만 했던 것은 아니다. 다른 방식으로 구성했을 때는 토큰 비용을 줄이는 효과도 경험했다.

이번에는 처음부터 무거운 모델이 모든 작업을 계획하고 지시하도록 하지 않았다. 먼저 루나가 작업의 난이도를 판단하고, 그에 맞는 모델 조합과 작업 그래프를 선택하도록 구성했다. 여기서 그래프는 어떤 모델이 계획하고 실행하며 검토할지 정해 둔 협업 흐름을 뜻한다.

예를 들어 한 그래프에서는 솔이 기본적인 계획과 평가를 담당하고, Gemini Flash가 명확한 코드 작성 작업을 수행하며, 아스트라가 최종 결과를 검토하도록 구상했다. 모든 단계에 가장 무거운 모델을 사용하는 대신, 역할에 맞춰 모델을 배치하는 방식이었다.

이 구조에서는 아스트라 같은 무거운 모델만 사용했을 때와 비교해 체감상 약 15~30% 정도 토큰 비용을 아꼈다고 생각한다. 다만 엄밀한 조건에서 측정한 벤치마크 수치가 아니라, 당시 사용하면서 판단한 절감 폭이다.

이 경험은 분명 의미가 있었다. 단순히 가벼운 모델에 일을 떠넘기는 것이 아니라, 작업에 맞는 협업 경로를 선택하면 토큰 비용 측면에서 이득을 얻을 수 있다는 가능성을 봤기 때문이다.

하지만 앞선 실험에서 드러난 문제까지 해결된 것은 아니었다. 복잡한 작업에서 실행 모델이 지시를 빠뜨리거나 검증을 끝내지 못하면, 검토와 재지시가 반복될 수 있었다. 비용을 줄이는 데 효과가 있었던 구조가 사람의 개입까지 줄여 주는 구조인지는 별도로 확인해야 했다.

필요한 것은 모델 수보다 협업의 기준

두 가지 실험을 거치며, 중요한 것은 에이전트를 몇 개 연결하느냐보다 작업의 난이도에 따라 어떤 모델과 협업 흐름을 선택하느냐라는 생각이 들었다.

가벼운 모델로 충분한 작업에는 가벼운 모델을 쓰되, 완료 조건을 충족하지 못하거나 같은 지적이 반복될 때는 실행 모델 자체를 바꿀 수 있어야 한다. 아스트라가 미완료를 정확히 지적해도 루나가 끝내 수행하지 못했던 경험을 생각하면, 검토 결과를 전달하는 것만으로는 부족했다.

또한 모델이 완료했다고 보고하는 것과 실제로 작업이 끝난 것은 다르다. 정형화된 테스트가 통과했더라도 요구한 E2E 검증이 빠져 있다면 아직 완료된 것이 아니다. 따라서 그래프마다 누가 계획하고 실행하는지만이 아니라, 무엇을 완료의 증거로 삼고 언제 다른 모델에 맡길지도 정해져 있어야 한다.

물론 모델을 바꿀 때마다 앞선 맥락을 처음부터 다시 읽어야 한다면 비용이 커진다. 작업의 목표, 변경 사항, 실행 결과와 검토 의견을 필요한 만큼 이어받는 방식도 함께 고민해야 했다.

같은 비용으로 더 많은 일을 할 수 있을까

처음 멀티에이전트를 고민한 이유는 단순히 에이전트를 많이 사용하거나 토큰만 아끼고 싶어서가 아니었다. 모델이 문제를 해결하지 못할 때마다 내가 직접 개입하지 않아도, 에이전트들이 협업해 끝까지 해결할 수 없을까 하는 질문에서 출발했다.

실험 결과는 한쪽으로만 정리되지 않았다. 루나가 난이도에 따라 작업 그래프를 선택하도록 했을 때는 체감상 15~30% 정도의 토큰 절감 효과가 있었다. 반면 아스트라의 지시를 루나가 끝까지 수행하지 못했던 경우에는 미완료 항목을 다시 확인하고, 내가 재지시하고, 결국 아스트라가 직접 마무리해야 했다.

돌이켜 보면 하나의 일을 끝내기 위해 같은 일을 두세 번 하는 느낌이었다. 그 과정에서도 토큰을 조금 아꼈을지는 모르지만, 사람이 개입하는 횟수와 다시 확인해야 하는 부담까지 고려하면 개선됐다고 보기는 어려웠다.

결국 멀티 에이전트를 통해 토큰 비용을 줄이는 것과 작업 완료까지의 전체 효율을 높이는 것은 서로 다른 문제였다. 작업에 따라 적절한 그래프를 고르는 것뿐 아니라, 어느 시점에 재시도를 멈추고 더 강한 모델로 넘길지, 그 판단과 검증을 사람이 아닌 에이전트가 얼마나 맡을 수 있을지도 중요했다.

아직 그 문제까지 해결한 것은 아니다. 다만 이번 경험으로 멀티에이전트의 가능성과 한계를 모두 조금 더 구체적으로 볼 수 있었다. 토큰 절감은 가능했지만, 내가 정말 원했던 개선은 사람이 중간에서 계속 챙기지 않아도 결과를 끝까지 책임지는 협업 구조였다.
